## 2026-09-26：V3 修复版有效，但当前配对实验低于 V2

V3 初轮的 profile assignment 因 Sinkhorn 指数化下溢而全为 0，已经单独标记为无效。修复方式是在指数化前对每行 logits 减去最大值，并增加 `loss_profile`、`profile_kl` 和 target confidence 的非零回归测试。修复版使用独立运行目录 `winpc_g5_v3_geodesic_s42_fix1`，于 2026-09-26 10:32:47 以 `EXIT_CODE=0` 完成，checkpoint 大小为 96,903,552 bytes；远端 GPU 检查显示空闲。

修复版的 profile 分支已经产生有效信号：train/validation 的 `loss_profile` 为 `0.1007/0.1446`，`profile_kl` 为 `0.3638/0.5309`，活跃 prototype 为 `51.0/45.68`，graph 连通分量为 `1`，不可达 pair 为 `0`。因此下面的 V3 数值可以用于和 V2 比较。

这组结果给出两个层次的判断。第一，数值实现已经通过有效性检查，初轮 V3 的全零 profile 问题不能再作为阻塞。第二，在同一 seed=42、10 epoch 和同一训练协议下，V3 没有复现 V2 的任务表现，整体 Acc 和 AUC 都低于 V2，synergy ROC AUC 下降 `0.0229`，unique2 Acc 下降 `0.0316`。因此当前证据不支持把 V3 直接替换为主方法。

这不是对 V3 跨 seed 性能的最终否定。当前只完成一组有效配对实验，且预算为 10 epoch；同时 graph 构造、geodesic temperature、Sinkhorn 设置和 prototype EMA 没有分别做消融。现阶段能够确认的是：测地轮廓在代码中确实工作，但它在当前固定设置下没有带来可见的信息增益，并且伴随整体性能下降。

接下来的处理应保持收敛：主线保留 V2 的 G0 证据，V3 作为有效但负向的 geodesic 对照写入实验记录；如果论文需要跨 seed 结论，只运行预先指定的独立 seed 配对，不同时搜索多个 graph 和损失超参数。没有新的独立问题和停止条件前，不启动长训练。

## 15. 2026-09-19 复核后的结论修正

旧结果中的数字来自真实日志，但实验协议和实现存在会影响解释的问题。因此需要区分数字是否真实与结论是否可靠。

### 仍然成立的事实

- 旧版程序能够完成训练和 probing；
- 两个 seed 的最后一轮 synergy 指标都略高于对应 Baseline；
- 四任务平均 acc@1 没有稳定优势；
- queue=1024 的旧版 profile accuracy 高于 queue=0。

### 不能继续沿用的解释

1. 旧版更新不是严格 EMA，旧结果不能代表修复后的方法；
2. UniGIR 原型初始化改变全局随机流，同 seed 的 Baseline 和 UniGIR 不完全是配对随机实验；
3. 每个 epoch 查看官方 test split，不能把其中最好 epoch 当作泛化性能；
4. Sinkhorn 强制 target assignment 接近均匀，因此 target usage entropy 和 active prototypes 不能单独排除塌缩；
5. profile accuracy 上升只说明掩码视图能拟合当前伪标签，不等于伪标签本身包含有用的 synergy 结构。

### 修复后的证据等级

当前仅完成单元测试和 64 样本端到端冒烟。它们证明代码链路可以运行，但尚未产生新的下游对照结果。对修复后 UniGIR 的性能判断应暂时记为未验证。

修复前和修复后的结果不得直接合并。GPU pilot 仍使用已经参与开发判断的 split，因此它只承担候选筛选，不能成为论文最终结果。

第二，synergy 的变化很小。acc@1 只提高 0.006，ROC AUC 只提高 0.001。当前研究最关心的 synergy 信号并没有像 share 和 unique1 那样明显，因此不能把平均指标的提升直接解释成 synergy 机制已经被验证。

第三，unique2 acc@1 下降 0.013，但 ROC AUC 上升 0.006。单个任务的 acc@1 和 ROC AUC 方向不完全一致，后续应保留两类指标，不能只报告一个有利数字。

### 运行和协议判断

这次运行解决了台式机部署中的主要工程问题：Windows 原生环境可以调用 GTX 1080 Ti；PyTorch CUDA、数据读取、修复后的 EMA、Sinkhorn profile、queue、训练、验证和最终 probing 均已跑通。UniGIR 的训练峰值显存约 8.2 GiB，当前 batch size 64 和 1024 pair 在 11.2 GiB 显存上可运行。

任务计划程序的定时触发方式可以让训练脱离 SSH 会话继续运行。第一次用 `/Run` 启动的 UniGIR 任务收到 Windows 控制中断，日志没有进入训练结果；第二次按定时触发后返回码为 0 并完整结束。以后 Windows 长任务统一使用定时任务或现场本地终端，不能依赖 SSH 前台会话。

### 当前结论

我把本次结果记为修复版开发 pilot 的初步正向信号，状态仍为 Uncertain。原因有三点：只有一个 seed；当前测试划分已经参与开发判断；synergy 的变化很小。下一步先按相同配置运行 seed=7、123，再检查三 seed 是否满足 G1 的 Weak Go 条件。如果不满足，停止扩大 UniGIR；如果满足，优先做 shuffled profile 和 queue=0 的机制对照，再考虑 MOSI。

## 2026-09-26：V2 梯度诊断与 V3 实现边界

为检查 G0 unique2 退化是否来自 profile loss 和 InfMasking 主损失的直接方向冲突，我对三个 UniGIR checkpoint 各读取 8 个训练 batch，分别计算两项损失在全部共享参数、encoder 和 projection head 上的梯度关系。诊断只读前向和反向，不调用 optimizer，不更新 prototype、queue 或 checkpoint。

| model seed | 全参数 cosine 均值 | profile/base 范数比 | 冲突 batch 比例 | encoder cosine | head cosine |
|---:|---:|---:|---:|---:|---:|
| 42 | 0.222 | 0.105 | 0/8 | 0.237 | 0.108 |
| 7 | 0.054 | 0.191 | 2/8 | 0.066 | -0.020 |
| 123 | 0.035 | 0.149 | 4/8 | 0.033 | 0.057 |

profile 梯度范数约为主损失的 10%—19%，三个 seed 的全参数平均方向没有稳定反向，但 seed=7 和 seed=123 的部分 batch 存在负 cosine，seed=7 的 head 平均 cosine 为负。因此，当前更合理的解释是局部梯度关系不稳定，unique2 退化还需要结合表征几何和任务方向分析，不能只归因于梯度冲突。

本轮已经实现 V3 的代码骨架：`losses/geodesic_profile.py` 从 detach prototype snapshot 构造对称 k-NN 图，用 Floyd–Warshall 得到 prototype shortest path，再用多个最近 prototype 近似样本到 prototype 的测地距离。完整视图的 geodesic target 仍使用 Sinkhorn，掩码视图使用负距离 softmax，EMA、queue、KL 和 V2 默认路径保持不变。V3 通过 12 项远端单元测试和 Hydra 配置解析，但尚未训练。

当前结论没有改变：G0 仍为 `Uncertain`；下一步应先做 V3 与 V2 的短预算成对实验，固定 seed、数据、alpha、queue、EMA 和训练预算，不能同时搜索 graph、alpha 和 queue。
