## 现在真实处于什么状态

### SSH 配置原理

现在缺少的是用户认证，不是服务器地址。前一次连接已经确认服务器地址可达，但本机 `id_rsa` 没有登录 `liangyl` 账户的权限。

SSH 登录分两步：第一步确认服务器指纹，防止连错机器；第二步确认登录用户，可以用密码或公钥。MobaXterm 现在能登录，说明你手里的登录方式有效，但它没有把密码提供给 `ssh-mcp`。公钥方案的作用是把一把新的公钥登记到服务器账户，私钥留在本机，之后 `ssh-mcp` 只用本机私钥完成认证，不需要知道密码。

因此，公钥配置只需要做一次。MobaXterm 用来完成第一次登记，Windows 的 SSH `config` 用来记住服务器地址和密钥路径，SSH Agent 用来在本机解锁带 passphrase 的私钥，`ssh-mcp` 最后复用这些设置执行只读命令。`config` 不是密码文件，公钥可以复制，私钥和 passphrase 不能复制给 Agent。

## 已经修复什么

### 方法实现

- 原型现在按 assignment-weighted centroid 做 EMA；
- 两个增广的完整视图合并后只更新一次原型，避免更新顺序带来偏差；
- 原型初始化使用独立随机生成器，不改变模型训练的全局 RNG；
- 默认原型数从 512 改为当前候选 128；
- 新增 prediction usage entropy、target confidence 和 prototype similarity，补足旧诊断指标的不足。

### 可重复性

- Python、NumPy、Torch 和 DataLoader worker 使用同一个实验 seed；
- 默认设置改为单设备、确定性训练；
- Windows 默认 `num_workers=0`，降低多进程内存风险；
- Baseline 和 UniGIR 后续使用相同 seed 时，不再因为原型初始化而改变后续随机流。

### 评测协议

- 正式训练固定 epoch；
- early stopping 默认关闭；
- 不再按官方测试指标选择 checkpoint；
- 只保存最后 checkpoint；
- linear probing 默认在训练完成后执行一次；
- synergy ROC AUC 仍是第一报告指标，但只用于最终比较。

## 修复是否跑通

六个单元测试全部通过，覆盖随机状态、EMA 公式、验证阶段状态隔离、反向传播、最终 probing 触发协议和 MOSI 下载目录创建。修复后的 64 样本、1 epoch CPU 冒烟也正常结束。

## 以前忽略的变量

1. Sinkhorn 会主动把 target assignment 拉向均匀，因此 target usage entropy 接近 1 不是独立的无塌缩证据；
2. 两个 seed 只能说明方向是否初步一致，不能估计稳定方差；
3. 训练 100 epoch 并在每个 epoch 做四个 probing，成本很高，还会反复查看测试集；
4. 训练任务不再一次性规划为固定的 15 个 run；每个决策门通过后才解锁下一批，避免把失败候选继续跑满；
5. 项目已有 22 个 checkpoint，占约 2.19 GB，D 盘剩余约 68.8 GB；长训练前要估算单个 checkpoint 大小和保留策略；
6. 当前 Git 工作区包含多项历史修改，尚未形成干净、可追溯的实验版本。
7. `max_size` 是 pair 数，不是图片数。`max_size=1e4` 对应 10000 个训练 pair；batch size 64 时每个 epoch 约 157 step；
8. 当前候选参数已经参考过旧 test split，仅增加 seed 不能消除方法选择对测试集的偏差。
9. No Queue 和 Batch-only Profile 在当前实现中是同一个实验：`queue=0` 时只使用当前 batch 做 Sinkhorn；
10. MOSI 的情感分类标签不能直接度量 synergy，只能检验真实任务迁移；

两组完成后检查训练是否跑满、最终 probing 是否只发生一次、运行时间、显存、synergy 指标和 profile 诊断。无异常后再运行 seed=7、123。

Strong Go 要求 3/3 seed 的 synergy ROC AUC 提升且平均绝对提升至少 0.01。Weak Go 要求至少 2/3 seed 提升且平均变化为正。两种情况都要求四任务平均 acc@1 的平均下降不超过 0.01。若不满足，不进入完整长训练。

pilot 有信号后，先运行 shuffled profile 和 queue=0。shuffled 与正常 UniGIR 接近时，关系轮廓解释缺少支持；应重写目标或停止。机制对照成立后，再准备 MOSI。完整 100 epoch Trifeatures 实验排在 MOSI 之后。

## 我现在应怎样表述结论

可以说：旧实现的两个 seed 在 synergy 上出现弱的同向信号，代码复核后发现可重复性、EMA 定义和评测协议存在问题，现已修复并通过轻量测试，正在等待 GPU 做修复版多 seed pilot。

不能说：UniGIR 已经稳定提高 synergy，queue 已经带来确定收益，或旧版高 target usage entropy 已经证明不存在塌缩。

## 服务器上的执行安排

服务器使用 Linux + SSH + Docker。现有 PowerShell GPU 脚本只保留参数参考，不能直接使用。运行时把代码、数据、结果和缓存分开挂载：代码用于读取，数据和 `/workspace/runs` 用于写入，checkpoint 不保存在容器内部。

GPU 空闲后先做宿主机 `nvidia-smi` 和 Docker GPU 预检，再启动指定 GPU 的容器。容器内先运行单元测试、Hydra 配置解析和 1 epoch 冒烟；通过后才做 G0 数据与版本固定。G1 按 seed=42 Baseline、seed=42 UniGIR 的顺序分开运行，每次只占用一个 GPU。两组结果和资源成本正常后，才解锁 seed=7、123。

服务器正式运行前需要确认课题组 Docker 镜像、SSH 账户、挂载路径、GPU 使用规则、存储配额和 NVIDIA Container Toolkit。完整流程见 `ProjectDocs/12_服务器SSH与Docker运行计划.md`。
