# winpc 实验监控与邮件通知规范

更新时间：2026 年 9 月 25 日

## 当前情况

G0 的六项正式确认已经完成。`winpc_g4_watchdog.ps1` 已经实际运行过，能够读取任务状态、日志、checkpoint 和 GPU 进程，并成功发送 `WAIT`、启动下一项和 `ALL_COMPLETE` 邮件。它目前把 G0 的六个任务、路径和参数直接写在脚本中，适合记录这一轮实验，不能直接复制给下一轮实验使用。

`winpc` 是我独占使用的 Windows 台式机，两张 GTX 1080 Ti 不需要等待课题组其他成员释放。watchdog 仍然保留 GPU 进程检查，但检查目的改为识别残留进程、误启动任务和脚本配置错误。只有当前配置中登记的实验进程和 Windows 桌面进程会被放行，其他 GPU 计算进程仍触发 `STOP`，防止在状态不清楚时继续启动下一项。

我新增了 `run_scripts/winpc_experiment_watchdog.ps1` 和 `run_scripts/winpc_experiment_watchdog.config.example.json`。以后每一组实验单独写一个配置文件，监控器读取配置中的任务顺序、运行名、日志根目录、checkpoint 根目录、训练预算和通知路径。G0 旧 watchdog 保留用于历史复核，后续新实验使用配置驱动版本。

本轮还新增了 checkpoint 只读评测和串行队列脚本：`winpc_checkpoint_eval.ps1` 负责单个 checkpoint，`winpc_checkpoint_eval_queue.ps1` 负责按配置顺序执行多个评测。它们使用独立的评测输出目录，不调用训练，不覆盖 checkpoint；每项开始、每 15 分钟等待、成功结束或失败都会通过同一套环境变量邮件通知。G0 的四项剩余 unique2 评测已经按 seed=7 Baseline、seed=7 UniGIR、seed=123 Baseline、seed=123 UniGIR 的顺序完成，队列日志记录为 `QUEUE_COMPLETE`，四项退出码均为 0。

本轮还新增了 `winpc_representation_diagnostics.ps1` 和 `winpc_representation_diagnostics_queue.ps1`。它们按配置串行读取六个 checkpoint，发送开始、等待、完成或失败邮件，并把逐样本 JSON/CSV、类别汇总和配对表示差值写入独立输出目录。诊断任务严格使用 `Sup + biased=false + task=unique2` pair，避免把自监督训练的 `biased=true` pair 混入 unique2 分析。

轻薄本只负责 SSH、读取日志、CPU 统计和发送邮件。训练和 checkpoint 评测都在 `winpc` 上运行，轻薄本不会被当作实验机器使用。后续每组 `winpc` 实验都应使用独立配置、独立任务名、独立目录和邮件 watchdog；只有当前配置的前一项成功且 GPU 没有未登记的计算进程时，才自动启动串行队列的下一项。

真实数据的 MOSI 任务使用 `run_scripts/winpc_schedule_mosi_experiment.ps1`。通用 watchdog 配置增加 `SchedulerType=mosi` 后，会按配置把 `ProfileLossWeight`、seed、epoch、batch size 和 `by_fit` probing 参数传给 MOSI 启动脚本；当前 alpha=0.125 的三 seed 对照已按该方式串行完成。

固定评测复核中发现，`mode=test` 如果只传 `trainer.default_root_dir`，旧版入口仍会把 TensorBoard 日志写到 checkpoint 目录下的 `test` 子目录。现在通过 `test_root_dir` 显式指定评测根目录，并要求每个 `RunName` 使用独立日志和预测目录。该问题已经在 winpc 的 8 项测试中复核通过，固定变换的六项评测也全部成功。

## 每个实验必须具备的目录

同一组实验中的每个 run 都必须有独立的：

| 内容 | 规则 | 作用 |
|---|---|---|
| 运行目录 | `RunRoot/RunName/` | 保存 Lightning 输出和 checkpoint |
| checkpoint | `RunRoot/RunName/checkpoints/last.ckpt` | 判断任务是否真正完成，也用于断点续跑 |
| 状态日志 | `LogRoot/RunName.status.log` | 保存实际参数、启动时间和 `END EXIT_CODE` |
| 标准输出 | `LogRoot/RunName.stdout.log` | 保存训练和最终 probing 输出 |
| 标准错误 | `LogRoot/RunName.stderr.log` | 保存 CUDA、数据和 Python 错误 |
| watchdog 状态 | `LogRoot/<ExperimentName>.watchdog.*` | 保存当前动作、事件和邮件结果 |

`RunName`、任务名和 checkpoint 路径不能在不同实验之间复用。这样即使某一项失败，也不会覆盖以前的日志和 `last.ckpt`。

## watchdog 的检查顺序

Windows 计划任务每 15 分钟运行一次 watchdog。每次运行按以下顺序处理：

1. 读取每一项的状态日志、标准输出、标准错误和 checkpoint。
2. 检查是否出现非零退出码、CUDA error、显存不足、Python traceback 或 checkpoint 缺失。
3. 调用 `nvidia-smi`，识别当前 GPU 计算进程。当前配置登记的实验进程和 Windows 桌面进程可以通过；未与当前配置关联的计算进程会触发 `STOP`。
4. 检查串行顺序。前一项没有成功时，后面的任务即使已经存在，也不会继续推进。
5. 前一项成功、当前 GPU 安全且下一项尚未注册时，才注册下一项 Windows 计划任务。
6. 将完整状态写入 JSON，并发送邮件。

watchdog 不会停止已有训练，不会删除任务，不会删除日志或 checkpoint。遇到异常时只写 `STOP` 和邮件，下一步由我读取原因后决定。

## 邮件规则

发信程序为 `run_scripts/winpc_g4_notify.py`，账号、授权码和收件地址只从环境变量读取：

- `INF_MASKING_MAIL_SMTP_HOST`
- `INF_MASKING_MAIL_SMTP_PORT`
- `INF_MASKING_MAIL_SENDER`
- `INF_MASKING_MAIL_PASSWORD`
- `INF_MASKING_MAIL_RECIPIENT`

winpc 的环境变量文件放在用户目录下的 `secrets/InfMasking/mail.env.ps1`，不进入 Git。轻薄本使用同一套发信逻辑，但本地密钥文件只保存在被 `.gitignore` 忽略的文件中。

正常运行时发送：

| 事件 | 邮件 |
|---|---|
| 仍有任务运行或等待 | 每次 15 分钟检查都发送 `WAIT` |
| 启动下一项 | 立即发送 `START_REQUESTED` |
| 非零退出、错误标记、checkpoint 缺失或存在未登记的 GPU 计算进程 | 立即发送 `STOP` |
| 全部完成 | 只在第一次进入 `ALL_COMPLETE` 时发送一次 |
| 邮件本身发送失败 | 写入 watchdog 邮件错误日志，不中断训练 |

旧版 G0 watchdog 之前会在每次 15 分钟检查时重复发送 `ALL_COMPLETE`。通用版本已经改为只在状态第一次变为 `ALL_COMPLETE` 时发送，避免完成后继续打扰。

邮件正文由 `run_scripts/winpc_watchdog_mail.ps1` 统一生成。正文保留时间、主机、实验名、动作、当前运行项、异常项、GPU 检查和完成数量；已经成功的历史 run 不再逐条列出，只写已完成数量，并提示到状态 JSON 查看完整队列。这样完成后的邮件不会把旧实验显示成当前正在运行的任务。

## 启动方式

新实验先复制 `winpc_experiment_watchdog.config.example.json`，改成独立的 `ExperimentName`、任务名、运行名、数据目录和参数。确认配置、代码和数据清单后，在 winpc 上用脱离 SSH 会话的 Windows 计划任务运行 watchdog。

计划任务的动作应调用：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File `
  C:\path\to\run_scripts\winpc_experiment_watchdog.ps1 `
  -ProjectRoot C:\path\to\InfMasking `
  -ConfigPath C:\path\to\run_scripts\my_experiment.watchdog.json
```

训练任务仍由 `winpc_schedule_experiment.ps1` 创建，并由 `winpc_start_experiment.ps1` 写入独立日志。SSH 断开不会影响已经注册的计划任务。

## 当前验证结果

- G0 六项任务均以 `EXIT_CODE=0` 结束并生成 `last.ckpt`。
- winpc 最近一次 watchdog 状态为 `ALL_COMPLETE`，通知状态为 `EMAIL_SENT`。
- G0 unique2 的四项只读 checkpoint 评测均以 `EXIT_CODE=0` 完成，队列状态为 `QUEUE_COMPLETE`，每项开始和结束邮件均发送成功。
- G0 unique2 的固定 test transform 六项只读 checkpoint 评测均以 `EXIT_CODE=0` 完成，队列状态为 `QUEUE_COMPLETE`，每项开始和结束邮件均发送成功。
- G0 逐样本 profile/表示诊断六项均以 `EXIT_CODE=0` 完成，队列状态为 `QUEUE_COMPLETE`，每项使用 4214 个 unique2 对齐 pair，开始和结束邮件均发送成功。
- winpc 的 GTX 1080 Ti 在评测结束后没有训练任务；`nvidia-smi` 只看到 Windows 桌面进程和评测 Python 进程，评测队列结束后 GPU 释放。
- 轻薄本的 `uv` 已能使用独立的 uv Python 3.13.11 发送通知。项目原 `.venv` 指向已失效的 Python 安装，因此本轮没有用它运行任何训练。

## 仍需人工确认的地方

配置驱动 watchdog 能检查任务、日志和 GPU，但它不能判断研究结果是否达到 Go 条件，也不能从 `acc_per_class` 自动推断语义类别。每一组实验结束后仍需要读取结果、核对配置和更新 `ProjectDocs/03_实验记录.md`、`04_结果分析.md` 及导师汇报文档。当前 G0 固定 test transform 复核确认 unique2 的配对 acc@1 在三个 seed 上均下降，下一项应该读取 profile 和表示诊断，不应直接增加训练并行度。

本轮 profile-only 评测和 MOSI alpha=0.125 对照复用了同一个队列和邮件通知链路。profile-only 的三个 UniGIR checkpoint 以及 MOSI 的三个低权重 checkpoint 均以 `EXIT_CODE=0` 完成。watchdog 只负责运行状态，最终的 profile、unique2 和 MOSI 结果仍需由结果分析脚本与人工判断研究含义。
